> **这份文件是给"下一个坑"用的。**
>
> 每章写完后按 `SKILL.md` 第三步第 8 条做一次 bug 归类。**判定为技能 bug 的，
> 修完必须在这里留一行**：症状 / 根因 / 修法 / 回归测试。

> 三条硬规矩：
> 1. **修逻辑就必须补 `selftest.py` 的回归测试**——没有测试的修复，下一个项目会再踩一次。

> 3. **只用文字/常量就能补的，不要改判断逻辑**；发现判断逻辑本身错了才改脚本。

## 政策变更（不是 bug，是作者定的规矩；记在这里免得下次被当 bug"修"回去）

- **P006 · 运行中发现问题必须查因、修掉、推回技能仓库（作者 2026，硬性要求）**
  **作者原话口径**："在运行过程中，如果有 bug，比如某一阶段运行没有达到理想状态，
  需要检查是什么问题导致，并修复问题，而不是置之不理；如果是 skill 的逻辑问题，就修复，
  并推送到 git 仓库，这是硬性要求。"
  细则写在 `SKILL.md` 的「硬性要求」一节（含 6 步流程与 4 种禁止做法）。要点：
  · **触发条件不是"报错了"**，而是**任何阶段"没达到理想状态"**——包括静默跳过、空结果被说成通过、
    假阳性/假阴性、文档与代码不一致、数字不自洽、产物不符合模板；
  · 顺序是 **定位根因（判归属）→ 给可复现证据 → 改技能并补回归+台账 → 自检全绿 → `git push`**；
  · **"是 skill 的逻辑问题"就改脚本**，不是改正文去迁就脚本；
  · 唯一例外是**创作分岔**（换主角/改档位/改结局），那要问作者。
  · 记为**政策**而不是 bug 的原因：它是**流程要求**，不是某个已知缺陷。
    以后再看到"看见了但没说""把失败说成通过"这类行为，**按违反本政策处理**，别当成风格差异。

- **P005 · 规模假设：单本 ≤100 万字（作者 2026 明确）**
  技能原先按"500 万字不崩"设计，并这样写进了 description。**作者明确：我们写小说最多不会超过
  100 万字**（按 2200 字/章 ≈ **455 章**）。据此校准：
  · `SKILL.md` 的 description 与"核心目标"**不再声称 500 万字**——那是未实测的过度承诺；
  · 「超长篇机制」触发点按百万字校准（50 万字 = 百万字书的**中后段**）；
  · **节点压缩从常规政策降为应急措施**：455 章的节点档案总共约 15-20 万字，
    **全量 grep 是毫秒级**——压缩换不来什么，却会真丢信息。只在"档案大到影响检索"
    或"要把全书交接点塞进一次上下文"时才做；
  · **角色分级的触发条件改为"具名角色超过 ~20 个"**（与字数无关，这个判据在任何规模都成立）；
  · 这是**减法**：按 5M 设计的那套，在百万字这个规模上属于过度设计。
  · **判断标准是"够不够用"，不是"能撑多大"。** 真要超过百万字，回来重新校准
    "节点压缩 / 角色分级"的启用点，别默认它还撑得住。
  · 顺带一条结论：这也让"**不做检索索引**"的决定更稳——100 万字约 2 MB 文本，
    grep 是毫秒级，索引的收益在这个量级本就很小，而"索引变旧"的风险是实打实的。

- **P004 · 允许一次"补写式纠偏"（2026，作者本人："允许注水，把该做的都做了"）**
  **这条解除了 P002 里"绝不补写"的绝对禁令**：低于目标字数下限时，现在允许做**一次**补写。
  > ⚠️ 下面四条护栏**不是作者原话，是我的实现选择**（作者只说了"允许注水"）。
  > 要放宽成"无功能内容也可以加"，就改这一条 —— 但先想清楚：那正是当初 P002 要挡的东西。
  1. **只补一次**（上限 1 轮）。补完**必须**跑 `style_audit --compare <补写前的版本>`：
     **AI 标记数变多就整轮回退**（B023 那道护栏；依据是 InkOS 实测"重写反而引入 6 倍 AI 标记词"）。
  2. **补写要有功能**：补"场景预算表"里已经存在、但没演出来的**动作 / 后果 / 反应节拍**，
     以及属于这个角色的具体行为。判据还是那一句：**加进去的东西有没有改变什么。**
  3. **绝不硬截断**。压缩侧同样只做一次，且**删减 >50% 直接回退原文、结果 <25% 原文直接拒绝**
     （这两条安全网取自 InkOS 旧版 CHANGELOG 的双保险，见 B024）。
  4. **P002 仍然成立的部分照旧**：不做字数**上限**、不追字数；超上限**不判也不提示**。

- **P003 · 过线标准：人工率 ≥95%（曾被放宽又改回，2026）**
  **现行标准：人工率 ≥0.95（对应 AIGC ≤0.05）。`DEFAULT_MIN_HUMAN = 0.95`。以人工率为口径。**
  完整经过：原本就是 0.95 → 作者一度要求放宽成"AIGC < 0.5" → 作者随后决定改回 0.95。
  `--min-human` 是主参数；`--max-aigc` 保留为换算别名（`max_aigc = 1 - min_human`）。
  > **教训：作者明确要守的线，不要随手放宽。** 放宽时我加了"这是下限不是目标"的解释，
  > 但那不能替代"先确认"。**动判定标准之前先问**——它影响的是整个工作流，
  > 不是一次可以试错的参数。（同一个道理在 B012：告警可以豁免，但必须显式、有依据。）

  附：`references/anti-ai-revision.md` 里也写着"人工率 ≥95%"，与现行标准一致，**不用改**。

- **P002 · 不做字数上限，且不追目标字数**（2026；其中"绝不补写"那半句已由 P004 修订）
  字数多少无所谓，**达到底线即可，绝不为了凑数字注水**。
  `series_audit` 只判下限（`WORD_LOW_RATIO = 0.9`），超上限不判不提示。
  写不够时该问的是"这场戏铺开了没有"，不是"往哪儿再加两句"——
  凑出来的句子会同时拉低 `mattr`、拉高 `tri_rep`，最后在朱雀那边付代价。

- **P001 · 本书区间豁免 `bands`**（2026）
  单句段占比实测 49%-65%，超出模板默认上限 45%，确认为刻意的短段排版 → 豁免到 0.70。
  写成基线 JSON 顶层的 `bands`，`--write-baseline` 重建时保留。
  **依据**：`window_pass` 同样长期偏低但**没有豁免**——因为它是节奏质量问题，不是风格选择。

### B035 · 索引用在最值的地方：写前简报 `brief`（2026）
- **动机**：作者同意把索引用进工作流，并授权"往最值的地方优化"。
  **最值的地方不是检索本身，而是写新章之前那一眼**——写新章最贵的错误是**与前文自相矛盾**
  （人还在别处、道具没交代、伏笔忘了推进），而这些恰好都能从索引一次问出来。
- **新增 `index_search.py brief <章号>`**，一次给三样：
  1. **本章出场人物最近一次在第几章**（隔了几章；≥8 章会提示"先回看那一章"；从未出现则标"本章首次出现"）

  3. **本章节点里提到的专有词**（含 `编号-07` 这类字母数字串、以及「」引起来的词）在全书的落点
- **真稿实测（第 14 章）**：出场人物 主角甲（最近第11章，隔3）/配角丁（第13章，隔1）/配角乙（第12章，隔2）；
  活跃伏笔 F001/F002/F003 都"隔 4 章"、F004/F005 已在本章推进（隔 0）。
  **这些信息以前要人翻五个文件、或者靠记性。**
- **接进流程**：`SKILL.md` 第一步"写前必读"新增第 8 条——每章动笔前跑一次 `brief`。
- **回归**：selftest [32] 新增 2 项（brief 能跑 / 章号不存在时退 2 而不是崩）。自检 234 → **236 项**。
- **设计边界（没变）**：`brief` 只**读**索引、只**给人看**，不参与任何判定；

### B034 · 加索引（SQLite + FTS5 trigram）——但把它做成"只能是缓存"（2026）
- **背景**：我先前拒绝过检索索引（理由：百万字下全量扫描够快 + 索引会变旧）。
  作者要求加 → 加，但**用三条约束把它做成不会坑人的东西**：
  1. **门禁一律不读它**：三个检查脚本继续直接读原文。一旦门禁依赖索引，索引一旧，门禁就开始骗人。
  2. **每次 build 都是全量重建到临时文件 + 原子替换** → **不存在"变旧的索引"这种状态**。
     这条直接消掉了我原先反对的主要理由。
  3. `meta` 表记章数/字数/schema 版本；`stats` 报"建完之后又新增了几章"。
- **实测出来的硬要求**：FTS5 可用，但 **`unicode61` 对中文子串检索返回空**
  （实测：「裤腿上」查不到「他把手在裤腿上擦了一下」），**只有 `trigram` 命中**；
  而 **trigram 要求 ≥3 字符** → 2 字人名（「老周」「主角甲」）**必须退回 LIKE**，
  否则最常见的查询反而查不到。两条都写进了注释与回归测试。
- **买到的东西**：`find`（道具/短语定位，`find "编号-07"` → 第1章、第4章 + 原文片段）、
  `who`（出场章号 + 中间断档）、`stats`、以及一个新的**可判定**检查 `verify`。
- **`verify` 第一版是废的（自己测出来的）**：原本做"节点声明出场 vs 正文找不到名字"
  → **14 章报 13 条**，因为第 1 章是第一人称（主角永远叫「我」）、其他角色多为「他/她」。
  **一个每章都响的告警比没有告警更糟**（B012/B017）。
  → **反转方向**成「**正文出现了、但节点没列**」（不判代词，是事实）+ `--min-hits 2`
  （路过提一次不算）→ 真稿 **7 个人名 / 14 章零误报**。
- **又一个 Windows 上的真 bug**：`cmd_find`/`cmd_who`/`cmd_stats` **开了 sqlite 连接却不关**
  → 文件被锁住，**临时目录都删不掉**（自检直接 `PermissionError` 挂掉）。
  已全部改成 `try/finally: con.close()`。**教训：CLI 里"进程退出会帮我收拾"是真的，
  但**被当函数调用时不是**——测试就是在函数里调的。
- **索引文件不进仓库**：`.gitignore` 加 `*.db`/`*.db.tmp`/`-journal`/`-wal`/`-shm`（重建秒级）。
- **回归**：selftest [32] 7 项（build / 原子替换不留 .tmp / ≥3 字走 FTS5 / **2 字退回 LIKE** /
  verify 正确时不报 / 漏列时报 / stats 正常）。自检 227 → **234 项**。
- **验证**：真稿 `find "编号-07"` → 第1、4章；`who 主角甲` → 6 章并列出断档章；`verify` → 没有漏列；
  `stats` → 与正文一致；`git check-ignore` 确认 `.db` 不进仓库。
- **教训**：**"加一个能力"和"加一个会被依赖的缓存"是两件事。** 索引可以是好东西，
  前提是**它不参与判定**、且**每次全量重建**——那样它连"变旧"的机会都没有。

### B033 · 压测脚本入册 + 它抓到的第二个 O(n²)（2026）
- **背景**：B032 的压测是临时脚本，作者同意收进技能 → 新增 `scripts/stress_test.py`
  （**开发期**用：造 455 章/百万字合成项目 + 进程内计时 + 30 个边界用例；退出码可当闸门）。
  改成**进程内计时**而不是 spawn 子进程，避免管道/沙箱依赖。
- **它立刻抓到 B032 漏掉的东西**：`series_audit：字数下限 + 遥测` 在 455 章下要 **7.13 秒**。
  根因：`count_chapter_chars` **每次调用都 `rglob` 两遍整个目录**，而它被逐章调用 →
  **O(章数²)**（455 章 ≈ 41 万次目录项扫描）。
  → 新增 `index_chapters()` **一次遍历建索引**，`check_word_floor` / `word_length_stats` 复用。
  **7.13 秒 → 3.30 秒**。另把 `count_chapter_chars` 的 docstring 写明"适合零散调用，
  循环里要自己先建索引"，防止后人再写回 O(n²)。
- **同时纠正我自己的一个错误**：B032 里那次"455 章实测"的 `series_audit` 数字**是不可信的**——
  那次 subprocess 调用**没传 `--chapters-dir`**，于是它扫的是真实项目的 13 章目录、
  而节点用的是合成的 455 个。压测脚本（这次把 `chapters_dir` 显式指向合成项目）才发现真相。
  **教训：性能测量要检查"被测输入到底喂进去没有"**——参数没传对的测量比不测量更糟，
  因为它会给出一个让你安心的数字。
- **两个失败的优化假设（如实记录，免得后人重走）**：
  · `ch not in PUNCT`（字符串 O(n) 扫描）→ 换 `frozenset`：**只省 0.2 秒**（3.32→3.13），
    说明瓶颈不在标点判断；
  · 逐字符 Python 循环 → 换**一次正则替换**（C 层）：series_audit 无明显变化（3.13→3.30，
    在噪声内），style_audit 小改善（2.62→2.49）。
  **两个改动都保留**（结果不变、语义更清晰、略快），但**不谎报收益**：
  3.3 秒里真正被拿掉的只有 O(n²) 那一块。剩下的 3.3 秒主要是 455 个小文件的读取与解码，
  **这个量级下可接受**（它每 3-5 章才跑一次，不是每章）。
- **回归**：selftest 只加一条"能导入应力测试脚本"的把关（压测很慢，不在自检里跑）；
  自检保持 **227 项全绿**；真稿三脚本结论不变。
- **教训**：**"第二次测量"往往比第一次更值钱**——第一次测出 3.5 倍"优化"（其实是输入喂错），
  第二次测出真正的 O(n²)。所以**把压测收进技能**这件事本身，就是这次最大的收获。

### B032 · 跑测试找出来的两个 bug + 一处 3.5 倍优化（455 章实测）（2026）
- **方法**：作者要求"跑测试、优化、修 bug"。做法三步：① 跑 227 项自检；
  ② **造一个 455 章 / 1,007,077 字的合成项目**（正好是 P005 的规模上限）实测三个脚本；
  ③ 对**全部新函数**做 **30 个边界模糊测试**（空文件、重复表头、缺列行、None 章号、
  空目录、target=0、别名在最后一行……）。
- **实测数据（455 章 / 100.7 万字）**：

  | 脚本 | 改前 | 改后 |
  | --- | --- | --- |
  | series_audit | **5.06 秒** | **1.46 秒（快 3.5 倍）** |
  | continuity_check | 1.01 秒 | 0.99 秒 |
  | style_audit | 2.98 秒 | 2.75 秒 |

  三个脚本在**百万字规模下全部秒级**。这条实测同时证实了 P005 的两个判断：
  "节点压缩在百万字以内不必要"、"不需要检索索引（全量扫描够快）"。
  另：`check_cross_chapter` 确认是**按句子归一化后分组的 O(总句数) 实现**，
  没有 O(n²) 风险（这是 455 章最可能出事的地方，专门查过）。
- **bug ①（会崩）：伏笔表某行少写一个 `|` → `IndexError`**
  `parse_foreshadowing` 里 `cells[i_status]` 没做越界保护（其它列都有）。
  **讽刺点**：B029 加这一层的目的就是"把畸形表格报出来"，结果它对畸形输入自己崩了。
  → 加越界保护；空状态在报告里显示为「（空）」而不是空白一片。
- **bug ②（会死循环）：`selftest.stat_fixture("")`**
  空文本时 `out` 永不增长 → 长度守卫永不触发 → **无限循环**（会挂住整个自检）。
  → 入口直接拒绝空文本。
- **优化：`series_audit` 把每章正文读了两遍**
  `check_word_floor` 与 `word_length_stats` 各自 `count_chapter_chars` 一遍 455 个文件。
  → 加可选 `measured` 缓存共用；**并用回归测试锁住"带缓存与不带缓存结果完全一致"**。
- **回归**：selftest [31] 新增 6 项（缺列行不崩 / 缺列行会被报出来 / 缓存与无缓存一致 /
  缓存确实被填 / 遥测一致 / stat_fixture 拒绝空文本）。自检 221 → **227 项**。
- **验证**：真稿三脚本结论不变；合成项目 30 个边界用例**崩溃 0 个**。
- **教训**：**"负责报畸形的层"自己必须对畸形免疫**——写检查的人最容易忘的，
  就是检查器自身的健壮性。以及：**优化必须带"结果不变"的回归**，
  否则省下的时间会以结论漂移为代价。

### B031 · 把剩下的优点也拿过来：schema 校验的等价物 / 伏笔三表对账 / 报告四态（2026）
- **动机**：作者要求"优点全部拿过来，哪怕重构"。重新审了一遍全部调研（不只先前那 9 项），
  把**还没拿**的三样落地。
- **① 未知字段/列名要报 —— InkOS 那条 zod `.strict()` 的等价物**
  它靠"未知字段直接拒绝"防住**拼错**与**死字段**（它自己就有 3 个死字段：`genreLock`/
  `allowedDeviations`/`fanficMode`——schema 合法、能写入、**全仓无读取点**）。
  我们保持 **markdown 作唯一真源**（不做 JSON 双轨，那是路线之争），但把"多出来的字段"当信号报出来：
  节点 front-matter 的 17 个合法字段之外的一律提示（并点名像"`hooktype` 应为 `hook_type`"这种拼错），
  伏笔表 12 个合法列之外的一律提示。
  **拿的是它的"行为"（未知即异常），不是它的"形式"（JSON+Zod）。**
- **② 伏笔表三处对账（此前完全没有）**
  我们的伏笔表其实有**三份互相不知道的账**：活跃表（状态）、回收记录表、"本章伏笔操作"里写的手工记录。
  三者各写各的 → 矛盾时静默。现在三处都查：
  · 同一编号同时出现在活跃表和回收记录 → **必须改**（已回收还占着那 5 条上限）
  · 活跃表里留着状态=「已回收」的行 → 提示移出
  · "本章伏笔操作"写了「回收：FN」但活跃表状态还是 已埋/推进中 → **必须改（说收了没收）**
  · 回收了活跃表里不存在的编号 → 提示（编号写错）
  口径同 InkOS 的 hook 状态机（已回收不可被改回、撤回需依据）。
- **③ 审查报告必须标"性质"（四态）**：新问题／**已解决**／中性观察／无法核对
  （口径同它的 `assessment = issue|resolved|observation|unavailable`）。
  **"已解决"必须单独标出来**，否则"这轮 5 条"读起来像问题越改越多；
  并明确区分**内容层面**与**执行层面**——**执行失败不是内容有问题的证据**。
- **没拿的三样（附理由，因为"拿过来"不等于"都塞进来"）**：
  · **唯一真源 JSON + markdown 投影**：与"markdown 是唯一真源"是路线之争；**只拿它的行为**（见①）。
  · **同人/续作的 canon 层**：作者不写同人 → 立刻变成它自己那种**死字段**（第 5 条教训）。
  · **多模型路由 / TUI / 守护进程**：依赖它自己的运行时；我们是 markdown+Python 脚本。

### B017 · 漂移告警刷成了噪音（2026）
- **症状**：13 章的项目跑出来 `必须改 0 ｜ 参考区间外 19 ｜ 漂移 20` ——
  一个干净的项目，漂移条目比参考区间还多。分布：`weak_adverbs_per_1k` 6 次、

  多一个「然而」就跨界。**相对容差用在小量级指标上，会把"一个词"放大成"风格漂移"。**
- **修法**：加 `DRIFT_MIN_ABS` **绝对下限表**，相对与绝对**同时满足**才报；
  `punct_cv` 也给下限（标点分布天生高方差，本书跨章 0.31-1.32）。
- **修的过程中我自己又犯了一次同样的错**：第一版把"被下限挡住的波动"每章打一行说明，
  13 章就多出 10 行噪音，漂移只从 20 降到 17。**这正是 B012 明令禁止的模式。**
  改成默认不打印、要排查时加 `--explain-drift`，才降到 **8 条真信号**。
- **顺带修掉一个浮点边界**：`tri_rep` 差值恰好 0.010、下限也是 0.010 时，浮点误差让它被判成
  "未超下限"，而打印出来的是"升了 0.01（绝对下限 0.01）"—— 自相矛盾。改成先 `round(...,6)` 再比。
- **回归**：selftest [19]（小波动不报 / 默认不打印说明 / `--explain-drift` 才说明 /
  明显变化照样报 / 差值恰好等于下限时要报）。自检 100 → 116 项。
- **验证**：真实 13 章稿 `0/19/20` → `0/19/8`；剩下 8 条都是真变化

  **必须改与参考区间条数完全没变** —— 修的是噪音，没有改动任何结论。
- **教训**：**"相对变化"必须和"绝对量级"一起看。** 阈值定在相对值上时，先问一句
  "这个指标的典型量级是多少"——量级越小，相对容差越像放大器。
  另外：**降噪的补丁本身也要按降噪标准再审一遍**（这一条我第一版就写错了）。

  · `series_audit.check_nodes` 同样加章号重复检测 —— **两边都报，不许给出不同答案**。
- **回归**：selftest [18]（子目录里的章节看得见 / 子目录布局下跨章重复照样报 /
  无章号文件会被提示 / continuity 报重复 / series 报重复）。自检 95 → 100 项。
- **验证**：拿**真实 13 章稿**做对照 —— `git worktree` 拉出改动前版本，三支脚本输出与改动后
  **逐行一致**。真实项目章节扁平、命名规范，所以这次改动对它零影响；
  这正是期望结果：**修的是潜伏问题，不是改现患**（改完不该顺手改动正在写的稿子的结论）。
- **教训**：**同一个事实被两个脚本各自推断时，必须共用同一套规则。**
  一个 `glob` 一个 `rglob`、一个用列表一个用字典，就会在边缘输入上给出互相矛盾的答案 ——
  而"两个工具说法不一致"比"某一方报错"更难被发现。
  另一个可复用的做法：改检查器之前先想"它对输入做了什么隐式假设"，再把假设**显式化成一项检查**。

### B015 · 带 UTF-8 BOM 的文件被静默漏读（2026）
- **症状**：两类，同一个根因：
  1. `foreshadowing/伏笔表.md` 若带 UTF-8 BOM，`series_audit` 解析出 **0 条伏笔** ——
     伏笔超期、主线必收这些检查**全部静默失效**，输出照样是"必须改：无"。
  2. `zhuque_check --key-file` 的密钥文件若带 BOM，读出的 key 前面挂着一个 U+FEFF，
     请求头变成 `Bearer \ufeffsk-...`，只会拿到 401，而报错会把人引去怀疑密钥本身。
- **根因**：所有读取都用 `encoding="utf-8"`，而 BOM 是**首行的第一个字符**：
  · 靠"行首是不是 `|`"认表的解析（伏笔表整份文件就是一节表格）第一行永远不匹配 →
    表头找不到 → `header` 保持 `None` → 之后每一行都被跳过，**一声不响**；
  · `.strip()` 不会去掉 U+FEFF，密钥里就带着它。
  其它读取点（节点 front-matter、卷纲、关系表、角色档案）当时**碰巧**没坏：它们的锚点不在第 1 行，
  或者有 `i < 40` 之类的兜底。**"碰巧没坏"不等于没这个洞。**
- **修法**：**读**全部改 `encoding="utf-8-sig"`（18 处）；**写**保持 `utf-8`（生成的文件绝不带 BOM）。
  `utf-8-sig` 读无 BOM 文件与 `utf-8` 完全等价，所以对现有文件是零行为变化。
- **回归**：selftest [17]（带 BOM 的伏笔表仍解析出条目 / 列值读对 / 密钥文件读出干净 key /
  **脚本生成的文件不带 BOM** —— 最后一条守住写入口径，防止有人把读侧的改法顺手套到写侧）。
- **连带**：把 `judge()` 里残留的行内字面量提成具名常量（`HARD_PARA_CHARS` /
  `HARD_DIALOGUE_RUN` / `HARD_SAME_LEN_RUN` / `REF_TRI_UNIQ` / `SHORT_SENT_CHARS` /
  `LONG_SENT_CHARS`）—— 文件头写着"常量（唯一权威）"，就不该还有匿名数字。
- **教训**：**"整份文件就是一张表"的解析，最怕首行被污染。** 要不要处理 BOM，不能靠
  "文件是我们自己生成的、不会有 BOM" —— 作者用记事本/Excel 改一次档案就会有。
  另一个值得复用的动作：改完用 `git worktree add --detach <tmp> HEAD` 把**改动前**的版本拉出来，
  **在同一份真实稿子上跑一遍、比对输出**（这次三支脚本逐行一致），
  这比只跑自检更能证明"这次改动没有改变行为"。

### B014 · 新死线被误报成"时间倒流"（2026）
- **症状**：第 1-2 章记的是"名单死线 D-0"，第 13 章启用的是"面板二十四小时死线 D-1"，
  `series_audit` 报 **"倒计时倒退：第 2 章 D-0 → 第 13 章 D-1"**。
- **根因**：`countdown` 是**一个字段**，单调性检查假设全书只有**一条**死线序列。
  可连载里"这条死线办完、下一条新死线开始"是常态，序列会重置——
  重置在检查眼里就是倒流。B011（可延期死线）只解决了一半：那一半是"同一死线被改期"，
  这一半是"换了一条新死线"。
- **修法**：加 `COUNTDOWN_RESET_MARK = "重置"`——值里带这个标记的章节会**清空序列重新起算**，
  此后新序列内部照样要求单调。两个标记语义分清：
  - `（可延期）` = 同一死线被人为推后，**跳过**检查
  - `（重置）` = 换了一条全新死线，**从这里重新起算**
- **回归**：selftest [14]（带重置标记不报、重置之后新序列内部倒退照样报）。
- **连带**：同一次还清掉了本书的一个**档案错误**——第 1、2 章的 `countdown: D-0`
  记的是**可被第三方改期的名单死线**，而项目自己的《时间线》规则明说它不该进字段。
  已撤掉，只留在时间线正文里。
- **教训**：**"检查假设的唯一性"是隐藏的 bug 温床。** 同一个字段被要求表达"多条独立序列"时，
  要么把序列身份显式写进数据，要么给一个明确的复位标记——不能指望数据永远只有一条线。

### B013 · 检查只报百分比，不报位置（2026）

### B036 · 卷纲模板自带的表头分隔行被当成数据行（2026）·照模板写就中招
- **症状**：照 `references/volume-outline-template.md` 写的卷纲，`continuity_check.py` 报一条必须改：
  「卷纲-第1卷.md 第44行：状态列写了「---」，不在允许取值 ['archived','done','draft','outline'] 内」。
  第 44 行是 `| --- | --- | --- | --- | --- |`——markdown 的表头分隔行，**上面根本没有状态值**。
- **根因**：`check_volume_outline()` 用 `re.fullmatch(r"[\d\-]+", cells[0])` 判断"这一行是不是数据行"
  （字符集里带 `-`，是为了容忍 `1-3` 这类章号区间）。分隔行的第一格是 `---`，**恰好命中这个字符集**，
  于是整行被当成章号 `---` 的数据行，最后一格 `---` 被读成状态列。
  **照模板写 = 必然误报**，而模板里就一直带着这行。
- **修法**：取完 `cells` 之后、判章号之前，先跳过"整行都是 `-`／`:` 的 markdown 分隔行"（空单元格不参与判定）。

### B037 · 倒计时一跳超过 1 天就永久刷提醒（2026）·阈值不适配本书

  时间线也记了"第2→3章跨十日，用时间标记过渡"。**提醒指向的问题不存在，但提醒不会消失。**
- **根因**：这个检查**只看 front-matter 的数字**（`cur_v - prev_v > 1`），

  书自己的规矩是"超 3 天给一个明确时间标记即可"，两者不一致，于是每次时间跳都刷同一条。
- **修法**：把阈值做成**本书区间豁免**（`bands.countdown_jump_days_max`，默认 1 = 行为不变），

- **教训**：**"提醒型检查"和"判定型检查"要分开对待。** 判定型（倒退）错了就是错；
  提醒型（跳跃）在正文已经满足要求时会变成纯粹的噪音，而**一条你学会忽略的告警，

### B038 · 换个工作目录跑，禁止矛盾扫描整段跳过（2026）·而"必须改：无"读起来像全过了

- **回归**：selftest（上溯能找到／找到的是项目里那一个／更深子目录也能找到／

  **显式路径找不到时照旧明说"已跳过"，且不触发回退**）。
- **教训**：**"检查被跳过"必须在结论行里留下痕迹，不能只在开头打一行提示。**

  **一个会静默降级的检查，比没有这个检查更危险**——它给的是虚假的绿灯。

### B040 · 空声纹块被判「必须改」，而那一刀该落在档案上（2026）
- **症状**：给还没台词的配角建了档案、`fingerprint` 块按规范留空（不登记没落地的细节），
  于是每次拿它跑 `--fingerprint` 都报 **"角色声纹【X】0 次 … 登记项：（全部缺席）"**——**必须改**。
  可正文怎么写都清不掉：一个空清单永远满足不了。
- **根因**：判定把两件事混成了一个分支——「登记了却零命中」（正文的问题）与
  「一条都没登记」（档案的问题）。提示语"登记项：（全部缺席）"还把后者说成了前者。
  连带后果很坏：**"零命中"从此被训练成噪音**，而它本来是抓"角色出场却没有辨识度"的那把刀。
- **修法**：`analyse` 里给每个角色多记一个 `registered`（登记了几条）；
  `registered == 0` → **建议改 + 明确写「无法核对」**（并指出该去补档案），
  `registered > 0 且 total == 0` → 照旧**必须改**。
- **回归**：selftest [7] 追加三条（空块不进必须改／但也不静默、明确报"无法核对"／
  **有登记却零命中仍判必须改**——这条是反向保护，防止放宽变成关掉）。
- **教训**：**"检查做不了"和"检查没通过"必须分成两种结论。** 把前者塞进后者，
  会得到一个永远清不掉的必须改；而人对永远清不掉的东西的反应，就是学会无视它——
  于是真正该抓的"零命中"也一起失效了。凡是"指标为 0"的判定，都要先问一句：
  **这个 0 是"对象写错了"，还是"我没拿到可判的东西"？**

### B043 · 三个检查器的退出码契约不一致，且没有任何文档（2026）·串联调用会看错
- **症状**：`continuity_check.py` 有"必须改"时**默认退 1**，而 `style_audit.py` / `series_audit.py`
  有"必须改"时**默认退 0**（只有显式 `--strict` 才退 1）。三个脚本是同族、天天一起跑，
  却有三套契约，而且**退出码语义在文档里一个字都没有**（只有 `quote_check.py` 的 docstring 写了）。
  后果有两个方向：把 `continuity_check` 串进脚本链会**意外中断后续步骤**；
  以为"退 0 = 没问题"的人，会把另外两个脚本的"必须改"读成通过。
- **根因**：三个脚本是不同时间长的，各自定义了自己的退出码；`--strict` 只在两个里实现过。
  **没有人从"这一族脚本的接口"这个层面看过它们**，所以差异一直没被发现。
- **修法**：① 给 `continuity_check.py` 加 `--no-strict`（只报告不设闸门，退 0）；
  ② **保留它默认退 1**——跨章一致性错了会让后面几十章建在错地基上，这里的"硬闸门"
  是有意的，不该为了表面整齐把它降级；③ 在它的模块 docstring 里写清三个脚本的契约
  与**故意不同**的理由。
- **回归**：selftest [38] 共 **4 项**（默认退 1／默认确实报了跨章重复／`--no-strict` 退 0／
  `--no-strict` 不减少报告内容——防止"放宽退出码"顺手把检查也放宽了）。
- **教训**：**"默认值不一致"本身就是一个缺陷，哪怕每一个默认值单看都合理。**
  同族工具必须有一份能一眼对完的契约表；差异要么统一，要么在脚本 docstring 里写明为什么不同。
  另外：**放宽退出码时一定要同时断言"报告内容没变"**——否则"不设闸门"很容易滑成"不做检查"。

### B042 · 引文核验抽出 0 条引文，却打印"全部引文都能在正文里字面搜到 ✓"（2026）·空结果假绿灯

### B045 · 主干的最后一个阶段（全书完结）只有脚手架，没有清单（2026）·作者问出来的
- **症状**：作者问"逻辑有这些吗：设定→大纲→规划→写章→完结"。对照下来前四段都硬，
  **完结这一环只有四处散落的脚手架**：总纲的「结局（先写死）」、主角栏的「最终选择」、
  悬念三层的「动机悬念→终卷」、卷纲的「卷末交接」。
  缺的是"确认真的收到了那个结局"这一步——活跃伏笔清零验收、悬念三层是否全揭、
  弧光最终选择是否落地、总纲「合」阶段对账、封版打 tag，**全都没有载体**。
- **根因**：主干是按**章循环**写的（写前→写正文→写后七步），卷级靠「卷末交接」收束，
  而**全书完结是不可回滚的一步**（写崩一章可以改，宣布完本之后读者就走了）——
  这样一步反而没有自己的流程，因为它"只发生一次"，不在每章循环里。
  **"只发生一次的事"最容易没有归属。**
- **修法**：新增 `references/completion-checklist.md`（七节：结局对账 / 悬念三层 / 伏笔清零 /
  角色交代 / 结构体检 / 归档封版 / 不许做的四件事 ＋ 完本报告模板）；
  在 `SKILL.md` 加「完结 / 收尾阶段」一节作为主干入口，写清两条**只在此阶段成立**的：
  ① **完结章不做章末钩子轮换**（要收不要留钩子；`series_audit` 照旧会报，按已知例外如实说明，
  不许为了消告警硬加钩子）；② 完结章**可以长**（上限本就不判）但**下限照旧**。
  文件索引与 README 的 references 份数同步更新（15 → 16 份）。
- **回归**：selftest [22] 追加两条——**SKILL.md 必须指向 `completion-checklist.md`**
  （防止它变成"文件在仓库里、主干却不指向"的孤儿文档），以及
  **必须写明"钩子轮换在完结章不适用"**（防有人为消告警给完结章硬加钩子）。自检 287 → **289 项**。
- **教训**：**流程里"只发生一次"的环节必须有自己的清单，否则它一定被即兴处理。**
  而"即兴完结"的代价是不可回滚的：连载可以修，完本不能。

### B044 · 文档里写死的"实测输出"没有东西替你核对（2026）·本轮就是这么发现两处漂移的
- **症状**：`README.md` 两处写"236 项自检"，实际早已是 **262 项**；
  `examples/README.md` 声称演示 1"建议改（2 条）"，实际是 **3 条**——
  `axes:`（变化轴）检查是后来加的，示例文档没跟上。
  两处都是**文档承诺与实测不符**，而**没有任何检查会因此失败**。
- **根因**：这些数字是**人手写进文档的**，脚本改了不会通知文档；
  也没有测试去读文档、跑示例、做对比。属于"没人负责的那一格"——
  与 B038/B039 同一形状（约定与实际脱节，且脱节时保持沉默）。
- **修法**：① 新增 selftest **[39]**：在进程内跑 `examples/` 的两条演示命令，
  核对 `examples/README.md` 承诺的条数（连载体检 5 必须改 / 3 建议改；
  单章预筛 3 必须改 / 4 参考区间外）与"第 1 章 613 字"这类关键数字；
  ② **自检项数自己核对文档**：所有检查跑完后，读 `README.md` 里的 "N 项自检" 与
  **实际总数**比对，不一致就 FAIL 并**指出该改哪两处**；
  ③ 两处漂移一并修正：README 的自检项数、示例文档的"建议改 2 条 → 3 条"。
- **回归**：selftest [39] 共 **6 项**（示例输出四类条数 + 字数 613 + 钩子词表提示）。
  其中"项数自指"这一项**必须写在所有检查之后**
  ——`checks` 是边跑边加的，写在前面会把自己也数进去、永远差 1（第一版就踩了）。
  另外「顶层条目 vs `└` 落点子条目」的口径也要分清，否则一个必须改会被数成 11 条（也踩了）。
  后续又补了两个"文档承诺计数"断言（黑名单条数、references 份数），**这两个当场又抓到一处漂移**：
  README 写"黑名单（59 条）"，实测 **63 条**（B015 那次 62 → 59 之后，黑名单又长过，文档没跟）。
- **教训**：**文档里的数字也是代码**，它需要属于自己的回归测试。
  凡是"文档声明 X，实际由脚本算出"的地方（条数、字数、项数、阈值），
  都值得让测试去读文档、跑一遍、对一次——否则每一次改进脚本，
  都在悄悄把这些承诺变成谎言。**而"看起来仍然可信"的文档，比明显过期的文档更危险。**

## 待观察（还没到能定性的程度）

- **`quote_check.py` 只认三种中文引号**（`「」`/`『』`/`“”`），报告若通篇用英文直引号
  `"…"` 则**抽出 0 条**。实测（2026 复核）：这类报告不会假通过——B042 之后它会明确报
  「无法核对」，比原来的假绿灯安全；但**闸门等于没开**。
  没顺手修的原因：直引号在英文/代码里是**兼作撇号与单位**的字符，加进去就有把
  `can't`、`3"` 之类当引文的风险；宁可不抓，也不要制造假阳性（B017 的教训）。
  真要修，口径应是"**成对**直引号且长度 ≥ `--min-len` 才算一条引文"，并配正反两路回归。

- `zhuque_check.py` 有接口解析的回归测试（夹具是**真实调用**抓回来的三份返回，见 selftest [11]），
  但仍没有 live-call 测试（需要密钥，且要花额度）。
- `continuity_check` 的"称呼契约"是启发式：分不清"叙述里的简称"和"对白里的称呼"。
  目前靠关系表里写 `叙述` 标记来豁免（B004 的配套）。若日后发现误报率仍高，再收紧。
- `MICRO_BEATS` 观察词表是按本书校准的，换题材要重挑。
- **`他说，` 出现在引文内部时，会被"重复开头"计入**：`“他说，示例核心台词。”`
  这种**引语里**以"他说，"起头的句子，`style_audit` 的开头统计分不清它是"叙述层的对话标签"
  还是"引文里的字样"。判定为**可接受的启发式误差**，没改脚本——
  那一轮它报的"他说，×3"里确实有 2 处是真的标签，**整条告警是有效的**；
  为区分"引文内／叙述层"去改开头检测，收益小于把好写法改坏的风险。
  遇见时改一下那句引文的措辞即可（真实处理：改成"原话是，……"）。
  **若同类误报变频繁，再回来做"引号内不计开头"。**
