# 维护这个技能：bug 归属与修复纪律

> 这份文档讲的是"检查报出异常之后怎么办"——它属于**维护技能**，不属于写作流程，
> 所以从 SKILL.md 挪出来，需要时再读（每章都要用到的判定表就在下面第一节）。

## 一、先判归属，再动手

检测报出任何异常时，**先问一句"这是本书的问题，还是技能的问题"**，再决定改哪儿。
判错了就会越修越歪：拿正文去迁就一个有 bug 的脚本，等于把好的写法改坏。

| 症状 | 归属 | 改哪里 |
| --- | --- | --- |
| 脚本报的东西**在正文里根本不存在**（假阳性） | **技能 bug** | 改脚本判断逻辑 + **补 selftest 回归测试** + 记 `skill-changelog.md` |
| 脚本/模板的要求**明显不适配本书**（如句长区间、单句段区间） | **技能问题（可用豁免）** | 在基线 JSON 写 `bands` 明确豁免，**不要**改成"以后忽略这条" |
| 脚本报暂停/跳过/解析失败 | **技能 bug** | 同上；顺带查是不是文件格式变了 |
| 正文与档案/关系表/提纲**对不上** | **本书问题** | 按事实优先级裁决，把结论**写回档案**（正文对就改档案） |
| 反复写不好、节奏塌、人物走样 | **本书问题** | 改正文；顺手问一句"这个坑技能能不能提前挡住" |
| 同一件事**第二次**发生 | **上次没修好** | 回去把根因写清楚，别再打补丁 |

## 二、技能 bug 的修复必须一次做全四件事

缺一不可：

1. 改脚本或文档
2. **补 `selftest.py` 回归测试**（没有测试的修复，下个项目会再踩一次）
3. 在 `references/skill-changelog.md` 记一条：症状 / 根因 / 修法 / 回归测试 / 教训
4. **推送到技能仓库**：`git add` → 提交信息写清"症状 + 根因 + 回归测试" → `git push`。
   **推之前自检必须全绿**（`python scripts/selftest.py`），推完报出提交号与自检项数。
   凭据只走 git 凭据管理器／环境变量，**绝不写进任何会被提交的文件**。
   只有在"技能目录不是 git 仓库"或"没有推送权限"时才可以不推，但必须**明说**是哪种情况，
   并给出 patch／diff。

> **这是硬性要求，不是建议**（作者 2026 设定，记在 `skill-changelog.md` 的 P006，
> 细则见 `SKILL.md` 的「硬性要求」一节）。触发条件不是"报错了"，而是
> **任何阶段"没达到理想状态"**——静默跳过、空结果被说成通过、假阳性/假阴性、
> 文档与代码不一致、数字不自洽、产物不符合模板，全都算。

## 三、别把告警调成背景噪音

> 如果某条告警每章都出现、你也每章都跳过它，那它要么该被修掉，要么该被 `bands` 明确豁免——
> **一条你学会忽略的告警，就是下一个真 bug 的藏身处**。
>
> 这不是理论：声纹告警连报六章"0~1 次"、被当成"按需改"忽略，
> 最后是一个女主出场 8 章、三条口头禅一条没用上（见 B003/B012）。
>
> 反过来，**脚本报的"参考区间外"不等于要改正文**。先判断是不是本书刻意的风格：
> 是，就写 `bands` 豁免；不是，才改正文。**唯一的错误做法是既不豁免也不改，让它一直刷。**

实测案例（B017）：13 章的项目里漂移告警 20 条，其中 11 条是"一章多一个「似乎」"级别的假信号 ——
降噪之后剩 8 条真信号，**必须改与参考区间的条数一条都没变**。降噪只该去掉噪音，不该改动结论。

## 四、改判断逻辑 vs 补文字

- **只用文字/常量就能补的，不要改判断逻辑**（改判定的风险远大于改文案）
- **动判定标准之前先问作者**（阈值、过线标准、政策都属于这一类）
- 修 BOM、换行、编码这类"静默失效"问题时，**先想清楚它还会在哪出现**——
  B015 的 BOM 让伏笔表解析出 0 条、密钥带 `\ufeff` 必 401，是同一类问题的两个面
- 改完之后**在真实稿子上对比改动前后的输出**：变的应该只是噪音或新增信息，
  **结论（必须改／参考区间条数）不应改变**；改了结论就说明动到了判断语义，要重新评估
