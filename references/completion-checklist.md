# 完结清单（收尾阶段）

> **为什么单独有一份**：`SKILL.md` 的主干是"设定 → 大纲 → 卷规划 → 章规划 → 写章 → 写后档案回写"，
> 卷末有「卷末交接」，但**全书完结这一环原来只有脚手架**——总纲里写死了结局，
> 却没有一份"确认真的收到了那个结局"的清单。
> 完结是唯一**不可回滚**的一步：写崩一章可以改，宣布完本之后读者就走了。
>
> **什么时候读**：进入最后一卷的后半段、准备写最后 10-20 章时读一遍，写最后一章前再读一遍。
> 它属于 `QC_FULL` 档位——**逐条过，不许跳**。

## 一、结局本身：确认收到的是"总纲写死的那个"

| # | 检查项 | 依据 | 怎么判 |
| --- | --- | --- | --- |
| 1 | **最后一场戏与总纲一致** | `outline/总纲.md` 的「结局」段：最后一场戏是什么、谁在场 | 逐句对照，**不一致就是必须改**（要么改正文，要么明确改总纲并在变更记录里留痕，不能含糊） |
| 2 | **主角的最终选择真的发生了** | 总纲「主角」栏的「最终选择」 | 正文里必须有**做出选择的那一下**，不能只写"他明白了" |
| 3 | **代价付过了** | 总纲「代价」栏 | 得到了就必须失去过；没失去 = 结局是白拿的，读者会觉得假 |
| 4 | **弧光终点与起点成对照** | 总纲「主角弧光路线」的 25%/50%/75% 三处 | 最后的心境要能看出**从哪走到哪**（不只是"变强了"） |
| 5 | **不引入新悬念** | 本清单第二节 | 完结章出现新钩子 = 读者认定你要烂尾 |

## 二、悬念三层：全揭，一个不留

总纲的「悬念三层」表（事件悬念 / 身份悬念 / 动机悬念）逐层对照：

- **动机悬念（贯穿全书，终卷揭晓）**：必须揭。这是完结章的核心兑现。
- **身份悬念（贯穿全书）**：必须揭或明确不揭（"故意不揭"要在总纲写明理由，不能是忘了）。
- **事件悬念（每卷至少 1 个）**：逐卷回查，**卷卷都要有落点**；漏掉的要么补一笔，要么改成明确不揭。

> 判据只有一句话：**读者追到最后一章，是因为想知道某事——那件事必须得到回答。**
> 用 `series_audit.py` 的伏笔/钩子输出做底稿，但**它只读节点 front-matter，不判语义**，
> 悬念有没有真的揭穿，只能人来读。

## 三、伏笔：活跃表清零或明确转结

```bash
python <skill-directory>/scripts/series_audit.py --plot novel/plot --target-words <单章目标>
```

- **活跃伏笔表必须为空**，或者每一条都写明"不完结、留给续作"（写进总纲，别只留在伏笔表里）。
- `series_audit` 报的"伏笔超期"在完结阶段**全部升级为必须改**——以前可以"转下一卷"，
  现在没有下一卷了。
- 长时间线伏笔（埋设章到回收章跨 100 章以上的）：**确认回收那一章真的落地了**，
  不是只在节点里写了"已回收"（节点自报不算，以 `chapters/` 正文实测为准）。
- 用 `index_search.py find <专有词>` 抽查几个核心意象/道具，确认最后一次出现有收束感。

## 四、角色：每个有名字的都要有交代

- 主线角色：结局在场或有明确去向。
- 支线角色（每卷 ≤2 条那条线）：线要收，或者明确"他的故事在别处"。
- 反派：动机闭环。**降智收场是最常见的烂尾形态**（见 `SKILL.md` 的 No-Poison 硬禁止）。
- 关系表核对：连载中改过的称呼/关系，最后一章是否与关系表一致（`continuity_check.py` 管称呼契约，
  但它不判"这段关系有没有收尾"）。

## 五、结构体检（完结前最后一次全套）

按 `QC_FULL` 跑一遍，**结论要绑定版本**（git 提交号或正文实测字数）：

```bash
python <skill-directory>/scripts/style_audit.py novel/chapters/最后一章-*.md \
  --blacklist <skill-directory>/references/ai-flavor-blacklist.md \
  --baseline novel/state/风格基线.json
python <skill-directory>/scripts/series_audit.py --plot novel/plot --target-words <单章目标> \
  --baseline novel/state/风格基线.json
python <skill-directory>/scripts/continuity_check.py --novel novel
python <skill-directory>/scripts/quote_check.py <审查报告> --chapter-dir novel/chapters
```

- **最后 3 章单独读一遍**：读者对结尾最挑剔，AI 味在结尾最容易暴露（总结腔、"从此以后"式收束）。
- **章末钩子的轮换在最后一章不适用**：完结章要**收**，不是留钩子。
  `series_audit` 仍会报钩子相关项，**完结章的这一条按"已知例外"处理，别为了消告警硬加钩子**。
- 字数：完结章可以明显长于常规章（这是**允许的**，上限本来就不判），但**下限照旧**——
  低于 90% 说明结尾写得太仓促。

## 六、归档与封版

1. **最后一卷归档**：`卷纲-第X卷.md`、`时间线-第X卷.md`、已回收伏笔、下线角色 → `novel/archive/`
2. **更新 `state/进度.md`**：标记完本、写实际总字数与总章数
3. **总纲回填**：把"计划结局"改成"实际结局"，差异写进设定变更记录
4. **git 封版**：`git tag v1-完本`（每卷有 tag 的照旧保留），确保全书可整体回滚
5. **`novel/` 全部提交**，工作区干净

## 七、不许做的四件事

- **不许为了完结而草率收束**：用一章把五条线一起"后来都好了"——那是加速烂尾，不是完结
- **不许把没写的当写了**：节点里写"伏笔已回收"而正文没有 = 档案在撒谎（`continuity_check` 会抓一部分）
- **不许在最后一章引入新设定/新角色**（除非总纲里本来就有）
- **不许把"检测全绿"说成"结尾写得好"**：脚本管结构，结尾好不好只能人读
  （汇报时用固定句式：`必须改 0 ｜ 脚本不查：结局兑现、悬念揭晓、弧光闭环、伏笔语义回收`）

## 附：完结报告模板（交作者前填）

```text
完本确认（截至 <git 提交号>，正文实测 <N> 字 / <M> 章）
- 结局与总纲：一致 / 差异点 <…>（已回填总纲）
- 悬念三层：动机 <已揭>｜身份 <已揭/明确不揭：理由>｜事件 <逐卷落点>
- 活跃伏笔：0 条未处理 / 转结 <编号>
- 主角弧光：起点 <…> → 终点 <…>，最终选择 <…>，代价 <…>
- 必须改：0 ｜ 脚本不查：结局兑现、悬念揭晓、弧光闭环、伏笔语义回收
- 人工复核（最后一章）：★ 项逐条过 <结论>
```
